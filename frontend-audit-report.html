1. Executive Summary

Puzzroo is a Next.js 16 App Router puzzle platform (Sudoku, Nonogram, CrossMath, Tangram, Chess) with Firebase Authentication, MongoDB/Mongoose backend, and a rich client-side game architecture. The codebase is functionally complete but has significant technical debt, inconsistent patterns, and several production blockers.

Verdict: The frontend is not production-ready. Three critical blockers (JWT in localStorage, missing error boundaries, wrong metadataBase URL) and one accessibility violation (pinch-zoom disabled) must be resolved before launch.

3. Architecture Assessment

Strengths

  • Clean separation of concerns: app/ for routing, components/ for UI, hooks/ for logic, lib/ for utilities/services
  • Shared code in shared/ package with path alias @shared/*
  • Game logic well-organized with per-game hooks and contexts
  • API client centralized with auth token refresh, retry, and error handling
  • Toast notification system with consistent key-based messages
  • Analytics batching with queueMicrotask and visibilitychange flush

Weaknesses

  • Deeply nested API route structure creates file sprawl (e.g., api/v1/games/crossmath/sessions/[sessionId]/verify/route.ts)
  • Duplicated logic across game hooks (session creation, save-move, completion reporting, localStorage caching, timer management)
  • No shared game state machine; each game reimplements playing/won/lost cycles independently
  • frontend-auth.ts is a 600+ line monolith mixing auth, profile, billing, and contact functionality
  • gameApi.ts has duplicated session management methods across games (e.g., startNonogramSession + createSession('nonogram', ...))
  • Inconsistent import patterns (@/* vs @shared/* path aliases)

4. Critical Bugs (Must Fix Before Launch)

#1 — metadataBase is ngrok URL (https://enhance-wrinkle-disjoin.ngrok-free.dev) — all OG images, canonical URLs, and Twitter card URLs point to a development tunnel. src/app/layout.tsx:17
#2 — maximumScale: 1 and userScalable: false in viewport meta tag prevents pinch-zoom — WCAG 1.4.4 failure, blocks users with visual impairments. src/app/layout.tsx
#3 — JWT access tokens stored in localStorage — vulnerable to XSS theft. Any injected script can exfiltrate the entire session. src/lib/auth/frontend-auth.ts, src/lib/api/client.ts
#4 — dangerouslySetInnerHTML used in layout.tsx for theme detection inline script — XSS vector if localStorage theme value is exploitable. src/app/layout.tsx
#5 — No <ErrorBoundary> wrapping the app — unhandled runtime error in any game component crashes the entire page with no graceful fallback. src/app/layout.tsx
#6 — sessionExpiredNotified flag in api client set to true on session expiry but never reset — subsequent 401s are silently swallowed. src/lib/api/client.ts

5. High Priority Bugs

#1 — useNonogram handlePointerMove uses document.elementFromPoint which can return null or wrong element during fast drag — race condition causing missed cells. src/hooks/useNonogram.ts
#2 — useSudoku reportWin deducts 20 points for hints even when score is 0 — Math.max(0, ...) not applied consistently. src/hooks/useSudoku.ts
#3 — useCrossMath history array stores full board copies for undo — unbounded growth causes memory bloat in long sessions. src/hooks/useCrossMath.ts
#4 — api client duplicates isTokenExpired logic with frontend-auth.ts — two independent implementations that could drift. src/lib/api/client.ts, src/lib/auth/frontend-auth.ts
#5 — Cross-Origin-Opener-Policy: same-origin-allow-popups set for ALL routes — overly broad, enables tab-napping on non-OAuth pages. next.config.js
#6 — No CSP header configured — mitigates XSS only through dangerouslySetInnerHTML which is itself a risk. next.config.js
#7 — Sudoku save move uses PUT but all other games use POST — inconsistent HTTP semantics. src/lib/api/gameApi.ts
#8 — withAuth route helper used in some API routes but manual auth() import used in others — inconsistent auth middleware. API routes

#1 — NonogramLobbyPage marked export default async but does not await anything — misleading code. src/app/nonogram/page.tsx
#2 — useSudoku StrictMode double-mount guard (_sudokuMountGuard) uses module-level mutable variable — not reset on route change. src/hooks/useSudoku.ts
#3 — useCrossMath usePatternMode = true hardcoded — dead code/future extension that is always true. src/hooks/useCrossMath.ts
#4 — Chess moveHistory stores full FEN strings for every move — memory bloat for long games. src/hooks/useChess.ts

8. Architecture & Code Quality

File Size & Complexity

  • src/lib/auth/frontend-auth.ts — 600+ lines, monolithic; should be split into useAuth, useProfile, useBilling composables
  • src/lib/api/gameApi.ts — 400+ lines with duplicated session methods; should use generic createSession/saveMove/completeSession only
  • src/hooks/useNonogram.ts — 600+ lines; drag state management is overly complex
  • src/hooks/useSudoku.ts — 500+ lines; timer and hint logic can be extracted
  • src/hooks/useCrossMath.ts — 500+ lines; history undo stores full board snapshots
  • src/hooks/usePolygonTangram.ts — 400+ lines; getTargetRotation does 8 rotations × 5 points per piece on each call

Duplicate Logic

  • isTokenExpired implemented independently in src/lib/api/client.ts and src/lib/auth/frontend-auth.ts
  • Session creation/cleanup pattern duplicated across all 5 game hooks
  • localStorage game state save/load pattern duplicated across all game hooks
  • Timer management with useEffect + useRef + clearInterval pattern duplicated in 4 game hooks
  • initSession function pattern duplicated across 5 game hooks
  • Module-level mount guard variables used identically in 4 hooks — should be a shared useStrictModeGuard() hook

13. Responsive Design Findings

  • Generally acceptable: Tailwind responsive classes used throughout (md:, lg: breakpoints), max-w-[1380px] container with mx-auto, mobile hamburger menu with md:hidden breakpoint
  • Issues: max-h-96 on mobile menu dropdown may clip on very small screens; clamp(16px, 2vw, 24px) on buttons may overflow on small phones; game boards have no horizontal scroll or pinch-zoom handling; Tangram pieces use absolute pixel coordinates for tray layout — may not scale on small screens; Chess board uses absolute pixel-based BoardGrid — responsive behavior unverified

14. State Management Findings

  • No global state management — all game state lives in component-local useState within custom hooks
  • Auth state scattered across localStorage, window.dispatchEvent('auth-change'), React context, and React Query — no single source of truth
  • ThemeContext only tracks theme; auth state is not in context despite both being in the same layout
  • React Query configured with staleTime: 5min and gcTime: 10min but refetchOnMount: false means initial load always shows stale/cached data
  • Timer state uses setInterval + useState pattern causing re-renders every second — should use useRef for interval and debounced state updates
  • history state in useCrossMath stores full board snapshots for undo — could grow unboundedly for long sessions

20. Performance Optimization Opportunities

  1. Replace setInterval timer re-renders with useRef-based interval that doesn't trigger React re-renders every second
  2. Add React.memo to game cell components (SudokuCell, NonogramCell, CrossMathCell)
  3. Implement request deduplication in the api client — avoid duplicate puzzle fetches
  4. Add AbortController cancellation to all fetch calls in the api client
  5. Use requestIdleCallback or Web Workers for puzzle validation computation in Nonogram and CrossMath
  6. Add code splitting — game components should be lazy-loaded with next/dynamic
  7. Switch from localStorage synchronous I/O to IndexedDB for game state caching
  8. Reduce history snapshot size in useCrossMath — store diffs instead of full board copies
  9. Add will-change CSS hints on animated/transformed elements
  10. Add prefetch to game lobby links so game data loads on hover

21. Refactoring Opportunities

  1. Extract shared useGameSession hook — handles createSession, saveMove, completeSession, cleanup — reduces code duplication across 5 game hooks (~2000 lines saved)
  2. Split frontend-auth.ts into useAuth, useProfile, useBilling composables
  3. Create shared useStrictModeGuard() hook — replaces 4 identical module-level mount guard patterns
  4. Standardize auth middleware across all API routes — use withAuth consistently
  5. Consolidate gameApi methods — remove game-specific aliases in favor of generic createSession/saveMove/etc.
  6. Consolidate isTokenExpired into a single utility used by both api client and frontend-auth
  7. Create shared useTimer hook — properly handles visibility API pauses, cleanup, and does not cause re-renders
  8. Create shared useUndo hook — for the undo/redo pattern used in CrossMath and Tangram
  9. Create shared usePuzzleLoader hook — handles caching, daily challenge detection, and error states

22. Missing Production Features

  • No <ErrorBoundary> — any runtime error in a game component crashes the entire page
  • No <Suspense> boundaries for async data (past puzzles, analytics, daily challenge data)
  • No loading skeleton components for game lobby pages or past puzzles grid
  • No empty state components — when a user has no past puzzles, no feedback is shown
  • No robots.txt route — search engines may not crawl correctly
  • No sitemap.xml route
  • No structured data (JSON-LD) for puzzles, games, or organization
  • No offline mode beyond the self-destructing service worker (no offline game play)
  • No keyboard shortcut help modal accessible from within games
  • No interactive tutorial — only static text descriptions
  • No manifest.json icons in multiple sizes — only a single SVG icon referenced
  • No Web Share API integration for sharing daily challenge results
  • No aria-live regions for dynamic game status updates (score changes, win/lose)
  • No focus trap in modal dialogs (promotion, win/lose, draw modals in Chess)
  • No prefers-reduced-motion respect — CSS animations play even for users who prefer reduced motion

25. Final Verdict

The frontend is NOT production-ready. The most critical issues are security-sensitive (JWT in localStorage, missing CSP headers, XSS vectors via dangerouslySetInnerHTML) and accessibility-breaking (maximumScale: 1 prevents zoom). These must be resolved before any public launch.

The codebase is functionally complete with good architecture intentions, but significant code duplication, inconsistent patterns, and missing production features (error boundaries, loading states, SEO infrastructure) need to be addressed.

Estimated time to production readiness: 2-3 weeks with a focused effort on Phase 1 + Phase 2 items.
